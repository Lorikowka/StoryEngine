## 1. Назначение

`Trigger System` — событийная подсистема Story Engine, позволяющая автору сюжета описывать реакцию мира на действия игрока через JSON-файлы и команды.

Система должна связывать события игры с уже существующими модулями:

- Quest System;
- Dialogue System;
- Narrative HUD;
- Interaction Hint System;
- Player Capability;
- сетевой синхронизацией.

Главная цель — дать автору возможность создавать интерактивный сюжет без написания Java-кода и без привязки логики к жёстким координатам.

Пример:

> Игрок взаимодействует с дверью → сервер проверяет условие → ванильное открытие отменяется → показывается реплика → запускается диалог или продвигается квест.

## 2. Основания и принятые решения

В текущем Story Engine уже существуют квесты, сюжетный чат, диалоги и Hint System. Старая позиционная Interaction System была удалена, поскольку дублировала ванильные взаимодействия, зависела от координат и усложнялась быстрее, чем приносила пользу.

В качестве основы принимаются следующие решения:

1. Триггеры являются событийными, а не координатными.
2. Сервер является источником истины.
3. Условия используют единый диалект с Dialogue System.
4. Триггеры запускают существующие системы, а не дублируют их.
5. Конфигурация хранится в `config/story_engine/triggers/`.
6. Конфигурация поддерживает hot-reload.
7. MVP ограничивается четырьмя событиями.
8. Зоны и визуальный редактор откладываются.
9. Список действий ограничивается контролируемым набором.
10. Клиент получает состояние подсказок от сервера, но не принимает сюжетных решений.

## 3. Границы MVP

### 3.1. События MVP

| Событие | Назначение |
|---|---|
| `INTERACT_BLOCK` | Игрок взаимодействовал с блоком |
| `INTERACT_ENTITY` | Игрок взаимодействовал с сущностью |
| `QUEST_CHANGE` | Изменился статус или прогресс квеста |
| `DIALOGUE_FINISH` | Диалог завершился на сервере |

### 3.2. Отложенные события

| Событие | Причина откладывания |
|---|---|
| `ENTER_ZONE` | Требует отдельной подсистемы зон |
| `EXIT_ZONE` | Требует отдельной подсистемы зон |
| `BLOCK_BREAK` | Можно добавить после стабилизации базовых событий |
| `ENTITY_KILLED` | Можно добавить после стабилизации базовых событий |
| `ITEM_OBTAINED` | Требует единой модели отслеживания получения предметов |

Зоны не входят в MVP. Для них позднее потребуется отдельный модуль с форматом областей, отслеживанием позиции игрока и обработкой входа/выхода.

## 4. Модель триггера

Триггер состоит из пяти частей:

```text
Источник события
    ↓
Фильтр цели
    ↓
Проверка условий
    ↓
Проверка доступности
    ↓
Последовательность действий
```

Формально:

```text
Trigger =
    Event
    + Target Filter
    + Conditions
    + Availability
    + Actions
```

### 4.1. Источник события

Определяет, какое игровое или внутреннее событие запускает проверку триггера.

### 4.2. Фильтр цели

Определяет, к какому блоку, сущности, квесту или диалогу относится событие.

### 4.3. Условия

Проверяют состояние игрока и мира:

- наличие предмета;
- наличие или отсутствие сюжетного флага;
- состояние квеста;
- завершённость диалога;
- другие условия, поддерживаемые `DialogueConditionParser`.

### 4.4. Доступность

Триггер может быть недоступен, если:

- он уже выполнен и имеет `one_time: true`;
- не выполнены условия;
- объект больше не имеет нужного тега;
- сценарист отключил его;
- другой триггер уже обрабатывает то же событие (см. уточнение в §9.3).

### 4.5. Действия

Действия выполняются в порядке, указанном в JSON.

## 5. Адресация объектов

### 5.1. Почему не координаты

Координаты плохо подходят для сюжетной логики:

- объект может быть перемещён;
- структура может быть экспортирована в другой мир;
- карта может быть изменена;
- один и тот же сюжетный объект может существовать в разных экземплярах;
- координатная конфигурация плохо переносится между картами.

### 5.2. Теги

Для MVP используются теги:

- Scoreboard Tags для сущностей;
- лёгкие маркеры `minecraft:marker` для обозначения сюжетных объектов;
- теги блоков через связанный маркер или отдельную адресацию.

Примеры:

```mcfunction
/summon marker ~ ~ ~ {Tags:["door_archive"]}
```

```mcfunction
/tag @e[type=minecraft:villager,distance=..3] add npc_judge
```

### 5.3. Ограничения

Тег не является полноценным уникальным идентификатором. Несколько объектов могут иметь один тег. Поэтому до появления отдельной системы идентификаторов необходимо определить:

- допустима ли обработка нескольких целей;
- должен ли триггер выбирать ближайшую цель;
- должен ли маркер хранить координату связанного блока;
- как обрабатываются дубликаты;
- как проверяется измерение.

В MVP рекомендуется использовать правило:

> Один сюжетный объект — один уникальный тег в пределах используемой сцены.

Это правило должно быть явно отражено в документации автора карты.

**Правка 1.1 — валидация дубликатов.** Правило само по себе не защищает от ошибки автора карты: если два разных объекта в одной сцене случайно получат одинаковый `target_tag`, поведение («ближайшая цель побеждает») будет тихим и незаметным. `TriggerManager` должен на старте/hot-reload сканировать зарегистрированные теги в разумном радиусе от каждого триггера и логировать предупреждение при обнаружении более одного объекта с целевым тегом. Это не блокирует загрузку триггера — это диагностика для автора карты. Пункт добавлен в §15.

**Дименшн-проверка.** Правило проверки измерения цели (открытый вопрос §19.4) не обязательно решать с нуля: аналогичная проблема кросс-дименшн-устойчивости уже решалась в Quest System (сохранение прогресса `BlockBreak`/`Kill` через смену измерения и рестарт сервера). При реализации `TriggerContext`/`TriggerMatcher` стоит опираться на тот же паттерн хранения и проверки dimension-id, что использует `QuestProgressTracker`, а не проектировать отдельный механизм.

### 5.4. Будущее расширение

В дальнейшем можно добавить поле `target_id` и отдельную систему регистрации сюжетных объектов. Это не входит в MVP.

## 6. JSON-конфигурация

Файлы:

```text
config/story_engine/triggers/<trigger_id>.json
```

### 6.1. Поля

| Поле | Тип | Обязательное | Назначение |
|---|---|---:|---|
| `id` | String | Да | Уникальный идентификатор триггера |
| `event` | String | Да | Тип события |
| `target_tag` | String | Для взаимодействий | Тег цели |
| `target_type` | String | Нет | Тип цели: блок, сущность, квест, диалог |
| `cancel_vanilla` | Boolean | Нет | Отменить ванильное действие |
| `hint_label` | String | Нет | Текст подсказки |
| `conditions` | Array/String | Нет | Условия |
| `actions` | Array | Да | Действия |
| `one_time` | Boolean | Нет | Выполнить один раз на игрока |
| `priority` | Integer | Нет | Порядок выбора при конфликте |
| `enabled` | Boolean | Нет | Включён ли триггер |

Значения по умолчанию:

```text
cancel_vanilla = false
one_time = false
priority = 0
enabled = true
```

### 6.2. Пример: осмотр улики

```json
{
  "id": "archive_clue",
  "event": "INTERACT_BLOCK",
  "target_tag": "clue_archive",
  "cancel_vanilla": true,
  "hint_label": "[F] Осмотреть",
  "conditions": [
    "has_quest:investigation",
    "!has_flag:archive_clue_found"
  ],
  "actions": [
    {
      "type": "story_tell",
      "speaker": "Мысли",
      "text": "На столе лежит документ."
    },
    {
      "type": "give_item",
      "item": "minecraft:paper",
      "count": 1
    },
    {
      "type": "quest_advance",
      "quest": "investigation",
      "task": "archive_clue"
    },
    {
      "type": "add_tag",
      "tag": "archive_clue_found"
    }
  ],
  "one_time": true
}
```

*(Правка 1.1: поле `speaker` в исходном примере содержало артефакт `"en"` — заменено на осмысленное значение по образцу примеров Narrative HUD.)*

Пример является проектным шаблоном. Конкретный синтаксис условий должен быть приведён к реальному формату `DialogueConditionParser` и существующего `node.json`.

## 7. Условия

### 7.1. Единый диалект

Trigger System не создаёт отдельный язык условий.

Условия должны использовать тот же механизм, который применяется в Dialogue System. Это предотвращает появление двух несовместимых способов описывать сюжетную логику.

### 7.2. Требования к парсеру

`DialogueConditionParser` должен:

- принимать условие из триггера;
- проверять его на сервере;
- возвращать однозначный результат;
- корректно обрабатывать неизвестные условия;
- выдавать понятную ошибку в лог;
- не выполнять побочных действий;
- быть пригодным для повторного использования.

### 7.3. Ошибочные условия

Если условие неизвестно или имеет неправильный формат:

1. триггер не выполняется;
2. в лог записывается ошибка;
3. сервер не падает;
4. остальные триггеры продолжают работать.

## 8. Действия MVP

Список действий:

| Действие | Назначение |
|---|---|
| `story_tell` | Показать реплику через Narrative HUD |
| `play_sound` | Проиграть звук |
| `give_item` | Выдать предмет |
| `remove_item` | Удалить предмет |
| `add_tag` | Добавить сюжетный тег |
| `remove_tag` | Удалить сюжетный тег |
| `quest_advance` | Продвинуть квест |
| `start_dialogue` | Запустить диалог |

Новые действия не должны добавляться автоматически. Каждое расширение требует проверки, не превращается ли Trigger System в отдельный скриптовый язык.

### 8.1. Порядок выполнения

Действия выполняются сверху вниз.

Пример:

```text
1. Показать реплику
2. Выдать предмет
3. Продвинуть квест
4. Добавить флаг
```

### 8.2. Ошибка действия

Для MVP используется политика `fail-stop`:

- если действие не выполнилось, последующие действия не выполняются;
- ошибка записывается в лог;
- игрок получает понятное сообщение только если это предусмотрено действием;
- состояние не должно частично изменяться без явного решения.

Полноценная транзакционность откладывается, но порядок и критерий успеха должны быть определены до реализации.

## 9. Правила выполнения

### 9.1. Серверный цикл

```text
1. Сервер получает событие.
2. TriggerManager находит триггеры соответствующего типа.
3. Проверяется фильтр цели.
4. Проверяются условия.
5. Проверяется one_time.
6. Выбирается порядок по priority.
7. Выполняются actions.
8. Обновляется PlayerCapability.
9. Клиенту отправляется обновлённое состояние.
```

### 9.2. Защита от повторного запуска

Для `one_time: true` необходимо:

- проверить флаг до выполнения;
- установить флаг после успешного выполнения;
- не запускать один и тот же триггер повторно в рамках одного события;
- корректно сохранять состояние после смерти и смены измерения.

### 9.3. Конфликт триггеров (уточнено в 1.1)

Если несколько триггеров подходят под одно событие, правило зависит от **типа события**:

**Для `INTERACT_BLOCK` / `INTERACT_ENTITY`** (физическое взаимодействие — один клик не может законно открыть дверь и одновременно начать диалог):

1. выбирается максимальный `priority`;
2. при равном приоритете используется порядок по `id`;
3. если один триггер отменяет ванильное действие, это решение принимается до выполнения действий;
4. выполняется **только один**, наиболее приоритетный подходящий триггер.

**Для `QUEST_CHANGE` / `DIALOGUE_FINISH`** (события состояния, а не физического клика игрока):

Одно изменение состояния может законно требовать нескольких независимых реакций в разных местах карты (например: обновление подсказки на одном объекте *и* отдельная реплика в другом месте). Здесь правило «один триггер» неоправданно ограничивает авторов — вместо него **выполняются все подходящие триггеры**, отсортированные по `priority` (для предсказуемости порядка реплик/действий), без взаимного исключения.

Причина исходного ограничения (см. пояснение GPT-версии 1.0) сохраняется, но только для случая эксклюзивного физического клика:

> Для одного взаимодействия (`INTERACT_*`) выполняется только один наиболее приоритетный подходящий триггер — это предотвращает случайное двойное начисление предметов, запуск нескольких диалогов и конфликтующие реплики. Для событий состояния (`QUEST_CHANGE`, `DIALOGUE_FINISH`) выполняются все подходящие триггеры.

## 10. Интеграция с Hint System

### 10.1. Ответственность клиента

Клиент отвечает за:

- поиск объекта под крестовиной;
- отображение подсказки;
- отображение текста `hint_label`;
- визуальные маркеры;
- отправку запроса на взаимодействие.

Клиент не решает:

- выполнены ли условия;
- нужно ли отменять ванильное действие;
- можно ли получить предмет;
- должен ли запускаться диалог.

### 10.2. Ответственность сервера

Сервер отвечает за:

- проверку события;
- проверку цели;
- проверку условий;
- выполнение действий;
- отмену ванильного поведения;
- изменение состояния игрока;
- синхронизацию актуальной подсказки.

### 10.3. Синхронизация

Предлагаемый пакет:

```text
S2CSyncTriggerHintsPacket
```

Пакет может содержать:

```text
target_tag
hint_label
available
cancel_vanilla
```

Синхронизация выполняется:

- при входе игрока в область видимости цели;
- при изменении квеста;
- при завершении диалога;
- при изменении сюжетных флагов;
- при перезагрузке триггеров.

Клиент использует пакет только для UI. Серверная проверка выполняется повторно при клике.

### 10.4. Важное ограничение — приоритетный риск этапа 6 (усилено в 1.1)

Текущая клиентская логика `VanillaActionResolver` должна быть проверена на совместимость с серверным состоянием. Нельзя считать, что передача подсказки автоматически решает проблему полного подавления ванильного взаимодействия.

**Это не рядовой пункт тест-плана, а известный архитектурный риск.** По текущему отчёту по StoryEngine, клиентская ПКМ-блокировка реализована через клиентское событие `InteractionKeyMappingTriggered`, которое отменяет только физический клик — при этом F-фолбэк идёт напрямую в `MultiPlayerGameMode` и это событие не затрагивает. Значит серверный `cancel_vanilla` через `PlayerInteractEvent.RightClickBlock`/`EntityInteract` перекрывает не обязательно тот же набор случаев, что сейчас перекрывает клиентская блокировка ПКМ — например, открытие GUI торговли у жителя может идти через другой путь, не полностью управляемый одним Forge-ивентом.

Необходимо протестировать по отдельности, до объявления этапа 6 завершённым:

- двери;
- сундуки;
- кровати;
- рычаги;
- рамки;
- жителей (открытие торгового GUI отдельно от простого interact);
- сущности с особым взаимодействием (например, лошади/лодки — посадка может обходить `RightClickBlock`/`EntityInteract` целиком).

## 12. Основные классы

### `TriggerDefinition`

Хранит данные одного JSON-триггера:

- id;
- event;
- targetTag;
- targetType;
- cancelVanilla;
- hintLabel;
- conditions;
- actions;
- oneTime;
- priority;
- enabled.

### `TriggerManager`

Отвечает за:

- загрузку конфигурации;
- хранение активных триггеров;
- поиск по типу события;
- поиск по тегу;
- **обнаружение дублирующихся `target_tag` в пределах сцены и логирование предупреждения (см. §5.3, правка 1.1);**
- hot-reload;
- регистрацию слушателей;
- передачу триггеров исполнителю.

### `TriggerContext`

Содержит данные конкретного события:

- игрок;
- уровень;
- измерение;
- блок или сущность;
- позиция;
- исходное событие Forge;
- связанные квесты и диалоги.

### `TriggerMatcher`

Проверяет:

- соответствие события;
- соответствие цели;
- наличие нужного тега;
- доступность триггера;
- условия.

### `TriggerExecutor`

Отвечает за:

- порядок действий;
- защиту от повторного запуска;
- обработку ошибок;
- обновление состояния;
- логирование.

### `TriggerAction`

Общий интерфейс действия:

```java
public interface TriggerAction {
    ActionResult execute(TriggerContext context);
}
```

Интерфейс является концептуальным. Конкретный тип результата и обработка ошибок должны быть согласованы с существующей архитектурой мода.

### `TriggerActionRegistry`

Регистрирует допустимые типы действий:

```text
story_tell
play_sound
give_item
remove_item
add_tag
remove_tag
quest_advance
start_dialogue
```

Неизвестный тип действия должен вызывать ошибку конфигурации, а не падение сервера.

## 13. Команды

Предлагаемый корень:

```text
/_story trigger
```

Команды MVP:

```text
/_story trigger reload
/_story trigger list
/_story trigger info <id>
/_story trigger test <id>
/_story trigger enable <id>
/_story trigger disable <id>
```

Команда привязки:

```text
/_story trigger bind <trigger_id>
```

`bind` пока считается дополнительной функцией. Для первой реализации достаточно ручного создания маркера и добавления тега.

### 13.1. Требования к командам

Команды должны:

- проверять права оператора;
- выдавать понятные ошибки;
- не изменять JSON-файлы автоматически без явного решения;
- показывать количество загруженных триггеров;
- сообщать об ошибках парсинга;
- позволять проверить конкретный триггер.

## 14. Hot-reload

При выполнении:

```text
/_story trigger reload
```

система должна:

1. прочитать все JSON-файлы;
2. проверить структуру;
3. проверить типы событий;
4. проверить типы действий;
5. проверить условия;
6. **проверить конфликты дублирующихся `target_tag` (правка 1.1, см. §5.3);**
7. построить новый набор конфигураций;
8. заменить активный набор только при успешной загрузке;
9. отправить клиентам актуальные подсказки.

Если один файл ошибочен:

- ошибка записывается в лог;
- остальные корректные файлы могут быть загружены;
- ранее активная версия ошибочного триггера не должна исчезать без предупреждения.

Рекомендуемая политика для MVP:

> Ошибочный файл не активируется, а ранее рабочая версия сохраняется до следующей успешной загрузки.

## 15. Логирование и диагностика

Система должна логировать:

- загрузку триггеров;
- ошибки JSON;
- неизвестные события;
- неизвестные действия;
- неизвестные условия;
- срабатывание триггера;
- отмену ванильного действия;
- ошибку выполнения действия;
- конфликт нескольких триггеров;
- **дублирующиеся `target_tag` в пределах одной сцены (правка 1.1);**
- hot-reload.

Для отладки желательно добавить режим:

```text
/_story trigger debug true
```

В debug-режиме можно показывать:

- найденную цель;
- подходящие триггеры;
- результат условий;
- выбранный приоритет;
- результат каждого действия.

## 16. Тест-план

### 16.1. Загрузка

- корректный JSON загружается;
- пустой файл не ломает систему;
- неизвестное событие выдаёт ошибку;
- неизвестное действие выдаёт ошибку;
- hot-reload обновляет конфигурацию;
- ошибочная новая версия не уничтожает рабочую старую;
- **дублирующийся `target_tag` в сцене логируется предупреждением, но не блокирует загрузку.**

### 16.2. Взаимодействие

- триггер блока срабатывает;
- триггер сущности срабатывает;
- ванильное действие отменяется только при `cancel_vanilla: true`;
- обычное взаимодействие не ломается без подходящего триггера;
- клиентская подсказка соответствует серверному состоянию;
- модифицированный клиент не может обойти серверную проверку;
- **каждый тип ванильного взаимодействия из §10.4 (дверь, сундук, кровать, рычаг, рамка, житель, специальные сущности) проверен отдельно на корректность отмены.**

### 16.3. Условия

- выполненное условие пропускает триггер;
- невыполненное условие блокирует триггер;
- неизвестное условие не вызывает падение;
- состояние квеста корректно читается;
- сюжетный флаг корректно читается.

### 16.4. Действия

- реплика отображается;
- звук проигрывается;
- предмет выдаётся;
- предмет удаляется;
- тег добавляется;
- тег удаляется;
- квест продвигается;
- диалог запускается;
- ошибка действия останавливает дальнейшую цепочку.

### 16.5. Повторное выполнение

- `one_time: true` срабатывает один раз;
- `one_time: false` может срабатывать повторно;
- состояние сохраняется после смерти;
- состояние сохраняется после смены измерения;
- двойной клик не вызывает двойную награду.

### 16.6. Конфликт триггеров (новое, правка 1.1)

- для `INTERACT_BLOCK`/`INTERACT_ENTITY` выполняется только один, наиболее приоритетный триггер;
- для `QUEST_CHANGE`/`DIALOGUE_FINISH` выполняются все подходящие триггеры в порядке `priority`.

## 20. Финальная рекомендация

Для Story Engine рекомендуется реализовать Trigger System как небольшую серверную событийную надстройку, а не как универсальный скриптовый движок.

Основная формула:

```text
Событие
→ фильтр цели
→ единые условия
→ проверка доступности
→ ограниченная цепочка действий
→ изменение состояния
→ синхронизация клиента
```

На первом этапе важнее добиться надёжной работы четырёх событий и понятного JSON-контракта, чем добавлять зоны, визуальные редакторы и десятки действий.

Главные критерии успеха:

- автор может создавать сюжет только через JSON и команды;
- ванильные механики не дублируются;
- сервер контролирует сюжетную логику;
- клиент отображает актуальную подсказку;
- триггеры не создают скрытых конфликтов;
- система остаётся расширяемой, но не превращается в отдельный язык программирования.
