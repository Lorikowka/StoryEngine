# Камера к NPC во время диалога — дизайн-документ

## 1. Проблема

Хочется, чтобы при открытии `DialogueScreen` камера плавно доворачивалась
на NPC, с которым говорит игрок, а при закрытии — плавно возвращалась.

Наивный подход — "запомнить NPC по какому-то ID" — не работает:

- NPC создаются и уничтожаются скриптами (HollowEngine, командные блоки),
  у каждой новой сущности новый `UUID` при заспавне. Постоянного,
  стабильного между рестартами/пересозданиями идентификатора у неё нет
  и не может быть.
- NPC необязательно принадлежит именно нашему моду - это может быть
  сущность из HollowEngine, ванильный моб, сущность из совершенно
  другого мода. У нас нет доступа к его внутренней системе идентификации
  (если она вообще есть), и полагаться на неё нельзя.

## 2. Решение: сессионный UUID вместо постоянного ID

Ключевая идея - **нам не нужен постоянный идентификатор**. Камера к NPC
нужна только на время одной сессии диалога (от открытия `DialogueScreen`
до его закрытия). Нам не нужно "помнить" сущность между сессиями,
рестартами сервера или пересозданиями - только знать, на кого смотреть
**прямо сейчас**, пока диалог открыт.

В момент, когда диалог стартует, сущность-инициатор точно жива - именно
она (через HollowEngine-скрипт, командный блок или что угодно ещё)
вызвала команду старта диалога. Поэтому:

1. Тот, кто запускает диалог, передаёт **живую ссылку на сущность** через
   обычный ванильный селектор Minecraft (`@e[...]`, UUID и т.д.).
2. Сервер резолвит селектор в `Entity` **один раз**, в момент вызова
   команды, и берёт из неё то, что нужно для камеры (позицию).
3. `UUID` сущности хранится **только на длительность сессии диалога**
   (в `DialogueSession`, который и так уже привязан к игроку на время
   диалога и не переживает рестарт/логаут - см. существующий дизайн
   Dialogue System).
4. После закрытия диалога сессия и всё, что с ней связано (включая этот
   UUID), просто перестаёт существовать. Ничего никуда не персистится.

Это полностью устраняет проблему "ID всегда разный" - мы никогда не
рассчитываем на то, что ID останется тем же между сессиями. Нам это и не
нужно.

## 3. Совместимость: работает с любой Entity, не только с NPC Hollow Engine

Решение сознательно построено на базовых, независящих от конкретного мода
типах:

- **`net.minecraft.world.entity.Entity`** - базовый класс, от которого
  наследуются вообще все сущности в игре, независимо от того, какой мод
  их заспавнил. Мы не завязываемся ни на какой конкретный NPC-класс
  (в т.ч. не на классы HollowEngine).
- **`EntityArgument.entity()`** - стандартный ванильный Brigadier-аргумент
  команды. Он резолвит любой валидный селектор или UUID в любую сущность
  в мире, независимо от её типа/мода-источника.

HollowEngine в этой схеме - **один из возможных источников** селектора
(его скрипт передаёт UUID/селектор сущности, с которой взаимодействует
игрок в момент клика), но с тем же успехом источником может быть:

- командный блок (`@e[tag=barman,limit=1,sort=nearest]`);
- функция датапака;
- любой другой мод, вызывающий ту же команду;
- ванильный моб или даже другой игрок (селектор не проверяет "является ли
  это NPC" - если сущность резолвится, она подходит).

Единственное требование - переданный селектор должен резолвиться в живую
сущность на сервере **в момент вызова** `/story dialogue start`.

## 4. Команда: `/story dialogue start`

> Старое имя `/dialogue start` остаётся рабочим алиасом.

Текущий синтаксис:

```
/story dialogue start <player> <id> [nodeId]
```

Расширяется необязательным аргументом-селектором сущности:

```
/story dialogue start <player> <id> [nodeId] [npcSelector]
```

- `npcSelector` - `EntityArgument.entity()`, **опциональный**.
- Если аргумент не передан - диалог работает как раньше, без привязки
  камеры (например, чисто текстовый нарратив "голос за кадром", без
  видимого NPC).
- Если передан, но не резолвится (сущности не существует к моменту
  вызова команды) - команда не должна падать с ошибкой из-за этого;
  достаточно залогировать предупреждение и запустить диалог без камеры,
  как если бы селектор не передавался вовсе.

Пример вызова из HollowEngine-скрипта (псевдокод, синтаксис скрипта не
принципиален для этого документа):

```
onInteract(npc, player) -> {
    runCommand("/story dialogue start " + player.name + " barman_greeting - " + npc.uuid)
}
```

## 5. Что уходит по сети (позиция, а не UUID)

Камера - чисто клиентская история (мы не двигаем реального игрока, только
подменяем, куда смотрит его локальная камера при рендере). Клиенту не
нужен `UUID` NPC и не нужно самому искать сущность в мире - это лишняя
работа и лишняя возможность рассинхронизации (сущность может быть вне
видимости/выгружена у конкретного клиента).

Поэтому в `S2COpenDialoguePacket` (и в последующих `S2CUpdateDialoguePacket`,
если NPC может двигаться во время диалога) передаётся уже готовая
**мировая позиция** NPC на момент отправки пакета, а не идентификатор:

```java
// Существующий payload дополняется опциональными полями:
public final class DialogueNodePayload {
    ...
    // null, если диалог без привязки к NPC
    @Nullable public final Vec3 npcPosition;
}
```

Сервер при формировании пакета:

```java
Entity npc = session.getNpcId() != null
        ? level.getEntity(session.getNpcId())
        : null;

Vec3 npcPosition = npc != null ? npc.position() : null;
```

Если позиция нужна с учётом высоты глаз/центра модели (чтобы камера
смотрела NPC "в лицо", а не в ноги) - берётся `npc.getEyePosition()`
вместо `npc.position()`. Итоговый выбор - вопрос вкуса при реализации,
на архитектуру не влияет.

## 6. Обработка исчезновения NPC во время диалога

`UUID` хранится в `DialogueSession` (сервер), а не прямая Java-ссылка на
`Entity` - потому что сущность может быть выгружена (чанк выгрузился) или
уничтожена (скрипт её убрал) в любой момент, и держать "живую" ссылку на
неё нельзя (это будет висячий объект, ссылающийся на мусор).

Поэтому каждый раз, когда нужна актуальная позиция (при открытии диалога
и при каждом обновлении узла), сервер **заново резолвит** сущность по
UUID:

```java
Entity npc = level.getEntity(npcUuid); // вернёт null, если сущности больше нет
```

- Если `npc == null` - сервер просто не включает `npcPosition` в
  очередной пакет (или включает `null`).
- Клиент, получив `npcPosition == null`, плавно возвращает камеру в
  обычное положение (см. §7) и дальше рендерит диалог как обычно -
  **сам диалог не прерывается**, потому что текст/варианты ответов не
  зависят от того, жив ли NPC. Пропажа NPC - не повод обрывать разговор.

Никакого краша, никакого специального состояния ошибки - просто мягкая
деградация до "диалог без камеры".

## 7. `DialogueCameraController` - план реализации

Клиентский класс, управляющий подменой камеры на время открытого
`DialogueScreen`.

### Что делает

- Перехватывает `EntityViewRenderEvent.CameraSetup` (Forge-событие,
  вызывается каждый кадр непосредственно перед рендером мира - именно
  здесь можно подменить позицию/поворот камеры, не трогая реальную
  позицию игрока и не влияя на управление).
- Пока `DialogueScreen` открыт и есть целевая позиция NPC - плавно
  интерполирует поворот (и, при желании, лёгкое смещение позиции) камеры
  от "как было" к "смотрим на NPC".
- При закрытии диалога (или при пропаже NPC, см. §6) - плавно
  интерполирует обратно к обычному виду from-behind-player.

### Набросок API

```java
public final class DialogueCameraController {

    private static Vec3 targetPosition; // null = нет привязки к NPC
    private static float blend; // 0.0 = обычная камера, 1.0 = полностью на NPC
    private static final float BLEND_SPEED = 0.08F; // за кадр, подобрать на глаз

    private DialogueCameraController() {}

    public static void setTarget(@Nullable Vec3 npcPosition) {
        targetPosition = npcPosition;
    }

    public static void clear() {
        targetPosition = null;
    }

    @SubscribeEvent
    public static void onCameraSetup(EntityViewRenderEvent.CameraSetup event) {
        boolean dialogueOpen = Minecraft.getInstance().screen instanceof DialogueScreen;
        float targetBlend = (dialogueOpen && targetPosition != null) ? 1.0F : 0.0F;
        blend += Math.signum(targetBlend - blend) * BLEND_SPEED;
        blend = Mth.clamp(blend, 0.0F, 1.0F);

        if (blend <= 0.0F || targetPosition == null) {
            return; // обычная камера, ничего не трогаем
        }

        // Поворот камеры в сторону NPC, смешанный с исходным поворотом
        // event.getCamera() даёт текущую позицию/поворот камеры этого кадра;
        // дальше - обычная математика "направление на точку" (atan2 по dx/dz
        // для yaw, atan2 по dy/расстояние для pitch), смешанная с исходными
        // yaw/pitch через `blend` (линейная интерполяция или easing на вкус).
    }
}
```

### Точки интеграции

- `DialogueScreen.open(payload)` / `doUpdate(payload)` - вызывает
  `DialogueCameraController.setTarget(payload.npcPosition)` (или `clear()`,
  если `npcPosition == null`).
- `DialogueScreen.onClose()` - вызывает `DialogueCameraController.clear()`
  дополнительно к уже существующему восстановлению `hideGui`.
- Регистрация слушателя - обычный `@Mod.EventBusSubscriber(bus = FORGE,
  value = Dist.CLIENT)`, как и у остальных клиентских оверлеев/хендлеров
  в проекте (`NarrativeOverlay`, `QuestKeyHandler` и т.д.) - для
  единообразия с уже устоявшимся в проекте стилем.

### Что стоит решить/подобрать при реализации (не архитектурный вопрос)

- Скорость интерполяции (`BLEND_SPEED`) и кривая (линейная/easing) -
  чисто на ощупь, играется руками.
- Двигать ли также позицию камеры (лёгкий "наезд" в сторону NPC), или
  трогать только поворот - как повернуть голову, оставаясь на месте.
  Начать стоит с одного только поворота - это безопаснее (меньше шансов
  провалить камеру в текстуры/стены) и уже даёт нужное ощущение.
- Что происходит, если NPC двигается во время диалога (патрулирующий
  моб, а не статичный NPC) - текущий дизайн уже это учитывает через
  переотправку `npcPosition` в `S2CUpdateDialoguePacket` при переходе
  между узлами, но между узлами (пока игрок читает текущую реплику)
  камера будет смотреть в последнюю известную точку, не следя за живым
  движением между обновлениями узла. Если нужно живое слежение - это
  отдельная, более сложная доработка (постоянная трансляция позиции, а
  не разовая на каждый узел), выходящая за рамки этого документа.

## 8. Итоговый чеклист реализации

1. Добавить опциональный аргумент `npcSelector` в `/story dialogue start`
   (`DialogueCommand.java`).
2. Сохранять резолвленный `UUID` сущности в `DialogueSession` на время
   сессии (не дольше).
3. Добавить `@Nullable Vec3 npcPosition` в `DialogueNodePayload` и
   заполнять его на сервере при каждой отправке
   `S2COpenDialoguePacket`/`S2CUpdateDialoguePacket` через повторный
   поиск сущности по UUID (`level.getEntity(uuid)`, `null`-безопасно).
4. Создать `DialogueCameraController` (клиент) с подпиской на
   `EntityViewRenderEvent.CameraSetup`.
5. Подключить `setTarget()`/`clear()` в `DialogueScreen.open()`,
   `doUpdate()` и `onClose()`.
6. Проверить сценарий "NPC исчез во время диалога" - диалог продолжается,
   камера плавно возвращается, без ошибок в логе.
